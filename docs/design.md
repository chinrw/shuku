# 服务端设计决策

每个书库实例只管理一个内容目录。需要分别管理普通漫画和同人志时，运行两个实例，各自配置元数据来源。Shuku 接收 LRR 的迁移数据，但不保留它的归档 ID，也不兼容它的 HTTP API 或 Perl 插件。

## 归档与扫描

- 原始归档文件始终不改动，也不重新打包；唯一的写操作是用户在详情页删除一本书时删掉它的文件。所有派生数据（缩略图、解压缓存、图片变体）放在服务自己的数据目录里，与内容目录分开。
- zip 是主路径：入库时解析一次中央目录，记录每个图片条目的偏移、压缩方式和大小，读一页只做一次定位读取。不压缩存储的条目直接按文件区间返回，deflate 条目解压后返回。
- 页面排序用自然序；忽略 `__MACOSX/`、`Thumbs.db`、`.DS_Store` 和以 `._` 开头的 AppleDouble 文件。
- 直接包含图片文件的子目录也是一本书（用户的书库里约 1200 个，LRR 不读）：页面清单格式和 ZIP 相同，条目名是文件名、偏移为 0；大小取其中图片的总和，`mtime` 列存的是文件夹本身的修改时间和每张图的文件名、大小、修改时间（纳秒）的 64 位摘要，只用来判断变化（`shuku_archive::identity`），新书的加入时间另取最新的修改时间；改成图片扩展名的 ZIP 按魔数当单独的归档，不算页面；快速指纹由每张图的文件名加 ZIP 同样算法的快速指纹合成，它也是图片 URL 的版本号；完整指纹依次读每张图。
- 固实 7z、RAR、tar 系列和 PDF 不在 M1 范围内。以后实现时，固实包在后台从块头流式解压、边解边写进磁盘缓存，非固实的按条目直接读。
- 入库时用 imagesize 只读图片头部，记录每页的宽和高。

扫描用快速指纹认回路径消失的归档，保留原来的 ID、人工元数据和进度；原路径还在的副本另算一本。快速指纹取文件大小及首尾各 64 KiB，整文件 BLAKE3 在后台补算。两者都不是主键。识别重新打包的书需要页级指纹，不在 M1 范围内。

个别页读不出尺寸时保留该页，宽高记为 0，并计入坏页数；ZIP 结构损坏时才整本失败。JPEG 标记段之间有杂字节时，跳过这些字节再读一次。监视器只触发扫描和指纹补算，不另写一套入库逻辑。文件消失不自动删记录：只删记录和连原文件一起删是两种操作，条件见 [API 的编辑和删除](api.md#编辑和删除)。

LRR 迁移可以先于扫描。按路径暂存的元数据在新书入库的同一个事务里套用。系列识别的优先级和路径示例见[系列和卷](server.md#系列和卷)。数据库中的 `volume` 是排序位置：话数允许小数，番外排在正篇后面，索引只需要系列内名次。

## 写接口与设置

网页端和 MCP 走同一套 API。MCP 工具把调用方的令牌带到进程内 HTTP 路由，不绕开认证或校验，也不提供删除文件的工具。新增工具时维护 `crates/shuku-server/src/mcp.rs` 的 `TOOLS`。阅读进度按客户端翻页时间而非请求抵达时间比较，以免离线设备补传时覆盖新进度。

归档编辑的校验在 `ArchiveEdit::validate`。单本经 `App::edit_archive` 写入；扫描批次已持有事务，先校验再 `apply`。替换或移除标签后，只有归档和 Tankoubon 都不再引用它时才删除标签记录。

扫描和服务设置在 `setting` 表中分组保存，用带 `#[serde(default)]` 的结构读取，旧库缺少新增字段不需要迁移。`--settings` 只覆盖文件里写了的字段，经 `update_settings` 走和控制台相同的校验。

## 内置元数据来源

不兼容 LRR 的 Perl 插件。常用的几个改成内置功能，放在 `shuku-metadata`，不做插件机制。每个元数据来源都是可选的，默认关着，不用的不需要配置：

- 文件名解析（LRR 的 Filename Parsing）、ComicInfo.xml、E-Hentai/ExHentai 元数据，以及 ETagCN。ETagCN 不只是翻译：它和 E-Hentai 插件做同样的查找，再用 EhTagTranslation 的 `db.text.json` 把结果译成中文。Shuku 把它拆成 E-Hentai 查找加一个翻译开关。用过 ETagCN 的 LRR 书库迁移过来后标签已经是中文（`女性:`、`语言:`），所以翻译后的结果照样存成中文标签，和迁移来的数据一致，不在显示时再译。
- Bangumi 和 AniList 给按卷出版的普通漫画用，按系列查（`series::series_query`：`series:` 标签、扫描认出的系列名、去掉卷号的标题，依次取第一个有的），不给标题，加作者、出版社或类型、标签和简介。同人志和普通漫画各跑一个实例，各自开关来源，不做按目录启用。
- 各来源的输入完全不同（文件名、归档里的一个文件、网络），没有共用的 trait，服务端按 `metadata::Provider` 分派。联网只经过 `http::Http`，测试换成假的。
- 和 LRR 一样只加标签、不删；标题按“替换标题”设置决定；来源地址和简介只在书还没有时写入，在写入的事务里判断。写入都经过 `edit::ArchiveEdit`，写不进的标签（带逗号、换行）先丢掉。
- 只对扫描新加入的书自动运行，从 LRR 迁移来的（套用了 `lrr_pending`）和移动了位置的不运行。文件名和 ComicInfo 在扫描的批次事务里写入；在线来源放进 `metadata_queue` 表（按书和来源），HTTP 服务里的后台任务逐本查，每个来源一个后台任务、各自限速（E-Hentai 4 秒、Bangumi 1 秒、AniList 2 秒），IP 被封、cookie 或令牌无效、网络不通时只暂停那个来源，那本书留在队列里。队列里的书不管自动运行开没开都会查。
- 在线来源打开 `review` 时结果存进 `metadata_candidate`（每本每个来源一条），由人或 agent 改写后批准写入或拒绝。这是给 agent 介入（例如翻译）留的口子，MCP 包的就是 `/api/metadata/*` 这几个接口。
- 设置存在 `setting` 表的 `metadata` 键里，E-Hentai 的 cookie 和 Bangumi 的令牌也在里面；设置接口只返回它们有没有设置，不返回值。
- 文件名正则用 Rust 的 regex 语法，LRR 的默认正则要把字符类里的 `[` 转义才能用（见 `filename::DEFAULT_REGEX`）。

以后需要下载器、更多站点或包装 gallery-dl 的子进程协议时再定接口。

## 后续范围

[M1 后端计划](plan/m1-backend.md)记录存储、归档、查询、服务端和迁移工具的验收标准。M2 的范围包括管理功能、Tankoubon 和给通用阅读器用的 OPDS（含 PSE）；这个分期不是待办清单。OpenAPI 等接口稳定后再加，现阶段接口契约见 [HTTP API](api.md)。

M3 的切换方案是让 Shuku 和 LRR 暂时共读内容目录，各写各的数据。下线 LRR 前逐本对比页面清单，并比较常用查询的结果和耗时。容量规划还需要真实书库的总大小、标签分布和页数；[现有存储与搜索基准](storage.md)用的是合成数据。

M4 规划用 Kotlin 和 Compose 做支持离线阅读的 Android 原生客户端。现有的桌面和 Android 应用是加载服务端网页的 Tauri 外壳，不是这个原生客户端。
