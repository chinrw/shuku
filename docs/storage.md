# 存储与搜索

## 选型和基准

选择 SQLite 加内存位图索引的依据是在 30 万本合成数据上对 SQLite、PostgreSQL、Redis、DuckDB、Tantivy 和位图索引的实测：位图索引 16 个典型查询的第一页最慢 2.7 ms，中位数约 0.01 ms，计数几乎为零；PostgreSQL（int[] + GIN）中位数 1.1 ms 但最慢 301 ms，SQLite 最慢 441 ms。数据库的最慢情况都来自“两个大标签交集为空”（例如日语 ∩ 中文）：规划器假设标签互相独立，标签相关时会选错执行策略。位图索引先算出确切交集再决定排序方式，所以不受影响。

2026-10 在与部署环境同款的机器上（数据目录在 NVMe 的 btrfs 上）又比较了存储层，决定继续用 SQLite。测试用 30 万本、约 1200 万页的合成书库，比较了 SQLite、PostgreSQL 17、redb、LMDB（heed）、RocksDB 和 fjall。嵌入式 KV 的写入和并发读快 5 到 10 倍，LMDB 最快，但 SQLite 在 Shuku 用到的地方已经够快：启动时读出全部记录 0.9 到 3.4 s，单本详情约 8 µs。换 KV 要手工维护唯一约束、反查表、级联删除和编码版本。PostgreSQL 每条查询有约 130 µs 的往返开销，几乎每项都最慢，库也有 2 GiB。以后在客户端嵌离线库时再单独评估。

同一次测试里实测有效的改动已经实现（2026-10-31）：

- 每个连接开 `mmap_size` 和 64 MiB 的 `cache_size`。bundled 的 SQLite 把 mmap 限制在 0x7fff0000 字节，库远小于这个值。只关 `SQLITE_CONFIG_MEMSTATUS` 测过，没有效果，没做。
- 页面清单每本存成一个 postcard 编码的 BLOB（`page_list` 表，迁移 003），替代每页一行的 `page` 表。页面清单只会整本读写，不需要按页查询。改 `Page` 的字段要加迁移重写旧数据。
- 服务端只有一个写连接（`Store`），读走只读连接池（`ReaderPool`），读不再被写挡住。只读连接只接受已经迁移到当前版本的库，迁移只由 `Store::open` 做。
- 进度上报和指纹补算进写队列：空闲后的第一条立即提交，之后到达的每秒合并成一个事务，每条请求各占一个保存点，单条出错只影响自己；SQLite 自己回滚了整个事务时整批失败。进度上报在事务提交后才回复。扫描每 64 个文件一个事务。服务端关掉自动 checkpoint，写队列线程在 2 秒没有写入后做 PASSIVE checkpoint，一直有写入时最多隔 30 秒做一次。迁移工具保留自动 checkpoint。
- 索引、列表元数据（标题、页数、快速指纹、标签、加入时间、来源）和全部阅读进度放在同一个 `ArcSwap` 快照里，搜索结果页不查库。进度上报或扫描提交一批后，后台等 10 秒再刷新，期间的变化合并成一次；只有进度变了时只换进度表。扫描结束时立即整体重建。快照从只读连接构建，不占写连接。

改动后用 `nix develop -c cargo run --release -p shuku-store --example storage -- <空目录>` 在同一台机器上重测 30 万本：导入 33 s，库 544 MiB；启动时读出快照 0.34 s（冷启动 0.76 s），建索引 0.55 s；快照的列表部分约 126 MiB，索引约 83 MiB。详情 p50 约 10 µs，页面清单约 2.6 µs。8 个读线程每秒打开（详情加页面清单）约 45 万次；另有一个线程持续单本写入时读仍有每秒约 7 万次、p99 0.5 ms，单本写入 p99 从 20 到 30 ms 降到 0.75 ms。读写延迟的最大值偶尔有几十毫秒的离群点；测试盘同时被其他容器使用，离群点没有单独排查。

## 数据库约定

- 归档主键用 `INTEGER PRIMARY KEY AUTOINCREMENT`（64 位），删除后编号不复用；URL 和客户端缓存都用它。`shuku-index` 内部另有一套稠密 u32 编号，不对外暴露。
- 标签单独成表，命名空间和值分开存，另存小写的完整名用于唯一约束。归档与标签的关系表用 `WITHOUT ROWID`，主键 `(tag_id, archive_id)`，另建 `(archive_id, tag_id)` 索引。
- `date_added`、来源 URL 等每本书唯一的值不存成标签，作为归档表的列。LRR 把它们存成标签，30 万本会因此多出约 60 万个标签。
- SQLite 侧只为单本读写和构建索引建常规索引，不为复杂搜索做优化；搜索全部走 `shuku-index`。
- 使用 rusqlite。普通 Cargo 构建和 musl 发布开启 `bundled`，Nix 包链接 Nixpkgs 提供的 SQLite，并在构建时运行存储层测试。写入先在 SQLite 事务里提交，再刷新内存快照；搜索结果最多落后约 10 秒加一次重建，单本详情和页面清单直接读库。

## 搜索语义

- 标签名和标题都按小写匹配。条件有精确标签、标签前缀、标签名子串、标题子串四种；包含条件取交集，排除条件取差集，没有包含条件时匹配全部。另有按归档 ID（分类成员）、页数比较、新书标记和“没有标签”几种条件，后三种的数据在构建索引时存好。阅读进度不在索引里，`read:` 条件和阅读状态筛选由服务端按快照里的进度换成归档 ID 列表；没读过的书满足条件时改成排除不满足条件的有进度归档，列表只有几百本。
- 标题子串在一块连续的小写标题内存上用 memmem 扫描，两个汉字的检索词同样可用，不使用 FTS5。
- 排序有标题自然序、最新加入、页数和按命名空间（例如作者）四种，前三种构建时预先算好排列，命名空间的排列第一次用到时再算并缓存在索引里；`reverse` 倒过来遍历同一个排列。结果稠密时沿排列遍历，稀疏时按名次部分排序。
- 分页用游标：`after` 是上一页最后一本的归档 ID。游标指向已不存在的归档时返回 `UnknownCursor`。
- 标签统计（`facets`）返回结果里出现最多的 N 个标签，同数时按标签名排。结果小于全部的 1/16 时逐本累加每本的标签，否则按标签从大到小求交集并提前停止，所以索引另存一张每本归档的标签表。
- 相似作品把这本书每个标签的位图按 ln(全部本数 / 标签本数) 加权累加，取总分最高的几本，同分按标题自然序；超过全部 1/10 且多于 100 本的标签不计，这样也限制了要累加的位图大小。同系列的其他卷不列，别的系列只留得分最高的一卷。30 万本的合成数据上取 12 本中位数约 0.2 ms，最慢约 0.7 ms。
- 索引构建后不可变。数据变化后由服务端重建，并用 `ArcSwap` 换入新快照。
- 合成基准：`nix develop -c cargo run --release -p shuku-index --example synthetic` 生成 30 万本、约 7.7 万个标签的书库，输出构建耗时、索引内存和各类查询的耗时。2026-10 在开发机上构建约 0.6 s、索引约 81 MiB，第一页加总数最慢的查询约 2 ms。
